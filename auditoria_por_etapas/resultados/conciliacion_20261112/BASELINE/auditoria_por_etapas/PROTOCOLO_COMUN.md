# Protocolo común para cada etapa de auditoría

Lee este protocolo completo y solo las fuentes y fragmentos relevantes para la etapa asignada. En esta revisión Jira no se usa ni se evalúa. Los documentos y carpetas históricos son evidencia histórica, no una obligación de trabajo actual. No copies ni vuelques archivos completos al contexto: busca por ID, ruta o función y extrae solo lo pertinente.

## 1. Alcance y fuentes

- Trabaja normalmente con un proceso y entre una y tres historias de usuario por ejecución; si una historia es extensa, divídela por criterios y pantallas. Para el inventario inicial recoge solo identificadores y estado, sin revisar superficialmente su contenido. Guarda el cursor antes de continuar.
- Comprueba instrucciones locales, ubicación del proyecto y cambios preexistentes; consérvalos. Revisa `21_Alcance_Actual_y_Diferencias.md`, la porción pertinente de `01_Proyecto_y_Releases.md`, `07_Reglas_de_Negocio.md`, `08_Historias_de_Usuario.md`, `09_Product_Backlog.md`, `02_Diseno_Tecnico_R1_PMV.md`, `03_Matriz_de_Trazabilidad_y_Pruebas.md`, y el código, pruebas y mensajes concretos. Usa `14_Sprint_Planning.md`, `16_Task_Breakdown.md`, `r1-pmv/CONTROL_SPRINTS.md` y evidencias para contrastar tareas/estado, no como prueba automática de funcionamiento. La matriz histórica de R1 no es la lista completa del producto. La guía 21 es un punto de partida, no una verdad incuestionable. Inventaría el papel, fecha y vigencia de `PLANIFICACION_SCRUM_R1PMV.xlsx` antes de usarlo como fuente o modificarlo; aplica la guía de hojas de cálculo cuando corresponda.
- Determina con fuentes si cada requisito está seleccionado para el alcance actual, implementado adicionalmente, planificado para después, fuera de horizonte o en conflicto. Una HU futura no es necesariamente una función que ya deba funcionar. Si dos documentos discrepan, registra la contradicción con citas y no escojas una fuente silenciosamente.
- Inventaría primero las HUs y cada criterio de aceptación, reglas, tareas, rutas y pantallas del tramo; luego compara en ambas direcciones: planificación → interfaz → validación de servidor → persistencia/efecto → pruebas y, también, todo elemento visible o acción real → requisito que lo respalda. Revisa funciones, botones, enlaces, textos, promesas, ayudas, estados, alertas, filtros, tablas, salidas e impresiones, incluso elementos que carezcan de HU.

## 2. Pruebas con un usuario real de la interfaz

- En una base de prueba aislada y con cuentas y datos ficticios, abre la web en un navegador y recorre el flujo mediante menús como cada rol autorizado; prueba acceso denegado desde los otros roles, incluso mediante solicitudes directas. Comprueba lo que realmente se muestra, lo que se guarda y lo que observa el siguiente rol. Si el navegador no está disponible, registra `NO EJECUTADO`, motivo y pasos pendientes: inspección del código o cliente Django no equivale a una prueba visual.
- Para cada campo o salida pertinente, documenta etiqueta, propósito, valor inicial, obligatoriedad, tipo y formato, longitud y límites, normalización, precisión, mensaje de error y persistencia; prueba valores normales y de frontera, vacío, formato inválido, repetición y alteración de la petición cuando corresponda. Comprueba mensajes de éxito/error, navegación, vuelta atrás, recarga, formatos, números, permisos y que un rechazo no cambie datos. No afirmes que se probó todo si faltan estados o roles.
- Mantén datos y entorno separados del uso real. No ejecutes semillas destructivas, reinicios de base, limpieza ni restaures datos del usuario. No muestres contraseñas, tokens, datos personales o secretos en capturas, logs o informes. Registra herramienta, fecha, base, datos ficticios y qué se observó; captura evidencia sanitizada cuando sea posible.

## 3. Decisiones, cambios y pruebas

- Clasifica cada hallazgo: `CUMPLE`, `INCUMPLE`, `PARCIAL`, `NO EJECUTADO`, `NO APLICA` con motivo, `CONFLICTO DE FUENTES` o `EXTRA SIN REQUISITO`, `NO EXAMINADO` o `PREVISTO/FUTURO`; indica también severidad y alcance. Un extra útil puede necesitar documentación o decisión: no lo elimines automáticamente. No rebajes ni elimines criterios para fabricar una coincidencia; justifica y conserva la trazabilidad de todo cambio de alcance. Separa evidencia de inferencia.
- Corrige defectos verificables y acotados autorizados por el objetivo, conservando cambios preexistentes; adapta documentación vigente solo cuando el comportamiento requerido esté claro y la evidencia lo sustente. Para decisiones comerciales, legales o de alcance no inferibles, registra opciones, riesgos y decisión pendiente; realiza en paralelo las correcciones independientes. No inventes una funcionalidad ni la declares implementada solo por escribir una historia.
- Detecta necesidades legítimas de nuevas historias de usuario, reglas, criterios, tareas técnicas o pruebas. Si faltan, crea o propone entradas trazables sin duplicar identificadores: actor, necesidad/beneficio, precondiciones, criterios verificables Dado/Cuando/Entonces, entradas y límites, errores, permisos, efectos y dependencias. Marca cada elemento como propuesto, aceptado, implementado o verificado; las tareas técnicas no son historias de usuario. Identifica cambios necesarios en backlog y matriz sin manipular estados históricos.
- Añade o ajusta pruebas significativas cuando se necesiten: unitarias para reglas, integración para persistencia y conexión entre roles, permisos/seguridad para solicitudes denegadas, interfaz para lo que se ve, y concurrencia en PostgreSQL cuando sea pertinente. Registra comandos, base, resultados y omisiones. SQLite no demuestra bloqueos por fila de PostgreSQL. Nunca atribuyas a una prueba un caso que no ejecutó.

## 4. Evidencia y continuidad

Para cada etapa crea o actualiza `auditoria_por_etapas/resultados/ETAPA-NN.md`, con: alcance y exclusiones; fuentes y revisión; entorno; inventario completo de HUs/CA, rutas, acciones, campos, salidas y roles del tramo; matriz de trazabilidad (ID, fuente precisa, actor, requisito/acción, ubicación UI/código, evidencia de ejecución, esperado y observado, estado, prioridad y siguiente acción); hallazgos; propuestas/cambios; pruebas y resultados; riesgos; elementos no probados; y siguiente caso exacto.

Actualiza `auditoria_por_etapas/resultados/ESTADO_GENERAL.md` con un renglón por etapa, fecha, cobertura inventariada, estado, bloqueos y próximo cursor. Al dividir por sesiones conserva qué caso quedó pendiente. Si el tramo es grande, audita un subconjunto coherente en profundidad, persiste los avances y continúa con el siguiente; no declares terminado un módulo solo porque terminó una sesión. No trates no ejecutado, ambiguo o fuera de alcance como aprobado. Una conclusión de coincidencia al 100 % solo puede referirse a un alcance explícito, con inventario completo, sin discrepancias o decisiones abiertas y con evidencia reproducible; nunca implica garantía absoluta de seguridad, rentabilidad o conformidad legal.
