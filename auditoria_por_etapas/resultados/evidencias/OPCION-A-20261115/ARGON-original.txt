$$\text{allocated\_to\_active\_sales} + \text{reserved\_for\_pending\_refunds} + \text{executed\_refunds} \le \text{gross\_confirmed\_amount}$$$$\text{refundable\_available} = \text{gross\_confirmed\_amount} - \text{allocated\_to\_active\_sales} - \text{reserved\_for\_pending\_refunds} - \text{executed\_refunds} \ge 0$$Cómo bloquea el ataque/error de dos reembolsos de S/ 7.00 sobre un pago de S/ 10.00 cuando el primero sufre timeout de red:Paso 1 (Reserva previa a la llamada de red): Cuando se solicita el Reembolso #1 por S/ 7.00, el servidor abre una transacción corta, ejecuta SELECT ... FOR UPDATE sobre PaymentCreditRecord(id=X) (gross_confirmed_amount = 10.00), verifica que refundable_available (10.00) >= 7.00, crea RefundAttempt #1 con idempotency_key única en estado RESERVED_IN_FLIGHT e incrementa inmediatamente reserved_for_pending_refunds = 7.00 (haciendo COMMIT antes de llamar a la API externa). Ahora refundable_available = 10.00 - 7.00 = 3.00.Paso 2 (Timeout en la llamada externa del Reembolso #1): Si la llamada HTTP al proveedor para el Reembolso #1 da timeout o respuesta ambigua 502/504, RefundAttempt #1 pasa a UNKNOWN_REQUIRES_RECONCILIATION y mantiene bloqueados los S/ 7.00 en reserved_for_pending_refunds.Paso 3 (Intento concurrente o posterior de un Reembolso #2 por S/ 7.00): Si otro request (o un reintento con distinta clave) intenta pedir un segundo reembolso de S/ 7.00, el SELECT ... FOR UPDATE lee refundable_available = 3.00 < 7.00 y rechaza la operación de inmediato con ValidationError, impidiendo que salgan 7 + 7 = 14 sobre un abono de 10.Paso 4 (Destrabe seguro de UNKNOWN_REQUIRES_RECONCILIATION): Solo se mueve de reserved_for_pending_refunds a executed_refunds (si el proveedor confirma que sí se ejecutó) o se libera de vuelta a refundable_available (si una consulta GET al proveedor confirma fehacientemente que el intento #1 no fue procesado, o tras reintentar con la misma idempotency_key).Trazabilidad por pagador individual en cobros con varios abonos
