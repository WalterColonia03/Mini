# Reproducir el corte académico del 20/11

El manifiesto paquete-entrega.json fija los 150 archivos enviados. Desde la raíz del proyecto ejecutar con el Python de r1-pmv/.venv el script preparar_paquete.py y pasar un directorio nuevo como argumento. El verificador comprueba cada SHA-256 e impide incorporar bases, .env, evidencias y datos personales al paquete. El manifiesto identifica código y configuración pública. Los secretos de ejecución se asignan por entorno.

Para el servidor, ejecutar en r1-pmv con APP_ENV=test: `python manage.py check`, `python manage.py makemigrations --check --dry-run` y `python manage.py test -v 2`. literales_entrega.py contrasta la redacción con respuestas de la suite identity y produce un JSON. Añadir esta carpeta a PYTHONPATH y ejecutar `python manage.py test literales_bordes.Edges.test_last_admin_and_empty_render literales_bordes.Edges.test_defensive_messages_at_http_boundary`. El diagnóstico idna.py recibe la ruta SQLite, abre en modo de lectura y solo imprime contadores. Los reportes corresponden al corte; guardar las salidas de futuras ejecuciones en una carpeta nueva.

Para concurrencia, AUDIT_PG17_BIN apunta al directorio con postgres.exe, initdb.exe y pg_ctl.exe de PostgreSQL 17. La corrida utilizó los binarios embebidos io.zonky.test.postgres:embedded-postgres-binaries-windows-amd64:17.10.0 con su checksum de distribución. pg17_entrega.py inicializa un clúster de uso exclusivo en TEMP, exige observar los PID bloqueados en las carreras y lo detiene al finalizar. chrome_entrega.py usa Chrome y Playwright con base SQLite propia y puerto de loopback. Ambas herramientas heredan los escenarios 02-E. El archivo y la fecha de la carpeta distinguen cada ejecución.

Para el ensayo remoto, desplegar el paquete verificado en el proyecto de pruebas Hobby y conectar una base PostgreSQL exclusivamente ficticia. Las variables son APP_ENV=demo, DJANGO_SECRET_KEY aleatoria, DJANGO_ALLOWED_HOSTS con el alias exacto, PGSSLMODE=require y DATABASE_URL privada. El despliegue se identificó por el ID en despliegue.json. Registrar si cambia. Se ejecutaron todas las migraciones sobre base nueva, luego se crearon los tres roles, una cuenta activa por rol con contraseña aleatoria y CAJA-01. El script publica_final.py prepara su producto, lote y turno de ensayo. Los scripts de navegador solo admiten el alias del ensayo. No usarlos sobre producción.

MMSTAGE señala el directorio privado de preparación con package/, .db.env del proveedor, django.key y fixtures.json que asocia cada código ADMIN/VENDEDOR/ALMACENERO con [correo, contraseña]. MM_PLAYWRIGHT señala la instalación de Playwright. Con PYTHONUTF8=1 ejecutar publica_final.py y después publica_atras.py. Ejecutar publica_limites.py para personal, acceso móvil y fronteras. Los resultados reportan únicamente aserciones. La última vuelta deja abierto el turno ficticio de S/ 50 y el borrador descartado. Las confirmaciones de alta adicionales utilizan identidades distintas.

Se verificó anonimato del acceso al formulario de ingreso y control de los datos por cuenta. El entorno remoto de pruebas usa una base temporal de 24 horas, sin costo. Vencida la base, el alias de Vercel por sí solo no permite volver a iniciar sesión. Para otra exposición usar una base aislada vigente y registrar un nuevo corte.
